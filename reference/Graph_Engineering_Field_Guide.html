01Implementation proposal

The operating model in one page

Make the project durable, not the conversation endless. Use agents for judgment and implementation; use explicit state, evidence, and policy to govern progress.

Graph engineering is an approach to organizing work and knowledge as versioned, typed, queryable relationships. Its practical value is continuity: an interrupted run, a replacement model, or a new contributor can reconstruct what matters without rebuilding the entire project history.

The anchor document frames the transition as moving memory and evaluation outside the context window. It recommends measured loops, preserved artifacts, explicit lineage, and persistent relationships before large-scale parallelism. This report keeps that framing and translates it into a reusable development operating model. [D1: pp. 6-7, 10-11]

01 / START SMALL

One bounded delivery loop

Begin with one writer, a named objective, an independent review where risk warrants it, and a fixed stopping policy. A swarm is not the starting requirement.

02 / PERSIST EVIDENCE

Remember what justified progress

Link the requirement, code version, test run, decision, and unresolved gate. Preserve failed approaches with their scope, not just successful summaries.

03 / RETRIEVE SELECTIVELY

Give each worker the right context

Build a small context packet from relevant current records, conflicts, interfaces, and known failures. Keep the underlying sources available.

04 / SEPARATE AUTHORITY

Do not confuse knowledge with permission

A stored claim cannot grant tool access. An agent-authored plan cannot authorize deployment, data disclosure, purchases, or changes to the quality bar.

05 / QUALIFY COMPLETION

A task is not done because an agent says so

Treat implementation, verification, real-world qualification, and release authorization as separate dimensions, supported by exact evidence.

06 / EARN COMPLEXITY

Measure before expanding

Add planning, extraction, new storage, specialist roles, or parallel workers only when a concrete failure or measured opportunity justifies the added system.

Who this guide is for

The target is a substantial software product built by a small team or an owner supervising coding agents: a user interface, backend services, persistent state, external integrations, meaningful domain logic, packaging or deployment, and real users. The work spans multiple sessions and has enough coupling that isolated task completion is not the same as a working product. This is a qualitative scope profile, not a claim that a particular line count or issue count makes graphs worthwhile.

The same pattern can support an engineering workstation, a business workflow application, a data platform, a developer tool, or a scientific analysis product. It is less useful for a short disposable script, a single-document answer, or independent tasks with no reusable state.

Recommended starting architecture
Keep the existing repository, issue tracker, and continuous integration system. Add a small version-aware work/evidence index, a context builder, and a bounded runner only where those capabilities are missing. Do not begin by replacing the product architecture or introducing a second authoritative roadmap.

How to read this report

For the conceptual model, read sections 2-5. For adoption, choose the new-project or existing-project track in sections 8-9. For implementation, use sections 6-7 and 10-15. For a pilot, go directly to section 19 and the downloadable templates in section 20. Every proposal is intended to be adapted to the project's actual risk, architecture, and available tools.

02Document framework

What a graph is doing for the agents

A graph is a set of identifiable things connected by named relationships. The useful question is not whether the diagram looks sophisticated, but which decisions those relationships enable.

A node represents something: a task, requirement, component, source document, claim, code version, or evaluation. An edge states a relationship: a task depends on another task, a run produced an artifact, or an evaluation supports a bounded conclusion. The relationship's type matters. MENTIONS does not mean SUPPORTS, and DEPENDS_ON does not mean APPROVED_FOR_RELEASE. [D1: pp. 6, 11]

Keep three graph meanings separate

GraphThe question it answersImportant constraint
Execution / task graphWhat may run next, and which prerequisites and gates must be satisfied?A dependency DAG has no prerequisite cycles. A workflow state machine may contain controlled repair loops; these are different structures.
Commit DAG / work lineageWhich version changed from which parent, and which experiments or implementations descend from it?A failed branch can remain useful evidence. Lineage alone does not establish correctness or permission to integrate.
Knowledge / evidence graphWhich claims, decisions, and entities connect, and what sources support or contradict them?The graph may contain cycles and competing claims. Connectivity is not proof, and an absent edge is not proof of absence.

The source explicitly separates the commit DAG from the knowledge graph. They connect through records such as a run produced this code version and this claim; an evaluation assessed that version; a source supports the claim. That separation should survive the implementation. [D1: p. 6]

What changes in everyday development

Instead of asking an agent to "continue the project," ask it to execute a particular contract against an adopted baseline. The system can then retrieve the architecture decisions that still apply, the failures that matter to this change, and the evidence needed for completion. When a dependency changes, it can identify the conclusions that need reassessment.

A graph is not necessarily a specialized database. A few relational tables or versioned records can represent the same relationships. The source recommends starting there. Dedicated graph storage becomes a deployment decision only when actual traversal, scale, concurrency, or operations requirements exceed the simpler design. [D1: pp. 7, 9]

Important limit
Graph engineering preserves claims and their support; it does not convert claims into truth. A neat graph built from incorrect sources can make errors easier to reuse. Correctness depends on source quality, identity resolution, validation, and the evaluator.
03Implementation proposal

Decide whether the approach earns its cost

Choose mechanisms to solve observed coordination and continuity problems. Do not turn every project into an agent-platform initiative.

The source's six selection questions concern verifiability, stable versus variable steps, independence, alternative lineages, cross-session persistence, and affordability. Its decision table on page 8 maps simple tasks to simple patterns and reserves larger orchestration for work that needs it. [D1: pp. 8-9]

A practical complexity budget

For each proposed addition, write down the failure it addresses, the smallest alternative, its maintenance burden, and the result that would justify keeping it. Examples include a context builder to reduce rediscovery, a task lease to prevent duplicate writers, or an evidence index to detect approvals for outdated code. "It might help the agents" is too vague to justify a new service.

Prefer a graph view over existing records before a new graph authority. A generated index can be rebuilt. A second independently editable roadmap requires synchronization, conflict resolution, and ownership. Those are product obligations, not free side effects.

Signals to defer or simplify

Defer semantic extraction when existing IDs and explicit links already answer the questions. Defer multiple writers when changes repeatedly touch shared contracts. Defer a broad architecture taxonomy when a small set of packet dependencies is sufficient. Defer unattended operation when success cannot yet be evaluated or when the effect of a failed external action is unknown.

Not all ambiguity must be eliminated before work begins. Product exploration, interface prototyping, and architecture experiments can proceed under bounded discovery contracts. Their deliverable is evidence or a decision proposal, not a falsely final implementation.

The simplest successful alternative is the baseline
Compare graph-assisted execution with the best lightweight process already available: a good issue contract, a short project map, version control, and working tests. Comparing against a deliberately poor giant prompt will exaggerate the value of the graph.

05Implementation proposal

Reference architecture: separate the responsibilities

A transcript should not be the database, workflow engine, permission system, and audit log. Keep these responsibilities explicit even when they share one process.

The anchor proposes five planes: control, execution, artifact, graph, and evaluation. These are logical boundaries, not a requirement to deploy five services. A pilot can implement them in one local application with separate modules and a single writer. [D1: pp. 7-8]

PlaneOwnsMust not silently own
ControlApproved plan version, eligibility, leases, budget reservations, timeouts, and escalation state.New product scope, relaxed acceptance criteria, or external authorization invented by the model.
ExecutionBounded model calls, isolated edits, tool invocations, process supervision, and candidate artifacts.Final acceptance, self-approved privilege expansion, or unrestricted changes to the evaluator.
ArtifactImmutable content versions, run logs, patches, screenshots, datasets, and retention metadata.An implication that a file exists merely because an agent named it.
GraphTyped relations among records, source references, version applicability, contradiction and impact links.A guarantee that an extracted relation is true or that every relevant dependency is known.
EvaluationNamed rubrics, deterministic checks, reviewer findings, domain oracles, and required live observations.Product authority or release permission merely because checks are green.

Choose authority once, by field

Keep requirements in the approved product specification or issue system; code identity in version control; test outcomes in captured run evidence; permissions in a trusted policy store; and the graph as an index or validated projection of those records. A decision can change a requirement only through its authorized revision process. An old issue, fresh code, and a recent agent summary can disagree; record the conflict rather than silently selecting whichever is easiest.

For multi-repository work, use a release manifest that pins the revision of every participating repository, dependency lock, schema, and fixture set. One commit hash cannot identify a distributed product. Cross-repository graph links should reference that manifest, not a floating branch name.

Development memory and product memory are separate

The development graph describes how the software is being built and why changes were accepted. A product-domain graph describes customer data, engineering facts, or workflow entities inside the shipped application. They may share design patterns, but should have separate permissions, namespaces, retention, and source policies. Internal developer notes should not automatically appear in a customer-facing agent's context.

Make replacement practical: the runner should be able to change models without changing the artifact contract; the graph index should be rebuildable from its authoritative sources; and a persistent store should be recoverable without reconstructing facts from chat transcripts.

06Implementation proposal

Design a small, trustworthy information model

Use stable identity, explicit versions, scoped claims, and reversible decisions. Start with the questions the system must answer, not an encyclopedic ontology.

The source's proposed vocabulary includes entities, claims, sources, artifacts, runs, evaluations, tasks, commits, and metrics. It requires sources or explicit inference labels for claims, authoring runs and versions for artifacts, identified rubrics for evaluations, and addressable superseded objects. The following schema extends those invariants for software delivery. [D1: p. 11]

Record typeMinimum useful fieldsWhy it exists
Task / criterionStable ID; authoritative reference and revision; outcome; prerequisites; scope; required evidence.Ties work to a bounded, approved obligation.
Artifact / code versionContent hash; authoring run; base revision or manifest; creation time; storage reference; data classification.Identifies exactly what was produced and preserves reproducibility.
Claim / decisionStatement; epistemic status; scope; source references; valid input versions; rationale; conflicts; supersession.Separates observations, hypotheses, inferred conclusions, and accepted decisions.
Source snapshotCanonical identity; immutable version or hash; source location; captured time; applicable time; permission label.Allows a reader to reconstruct what was available when the claim was made.
Run / evaluationAttempt ID; actual model/runtime; input fingerprint; commands; rubric revision; environment; outcomes; cost; limitations.Distinguishes an execution attempt from evidence of successful completion.

Identity: names are labels, not keys

A component called "Parser" in two repositories is not one entity. Two deployments of the same service have different operational identities. A renamed module can retain lineage without becoming identical to its old implementation. Use deterministic identifiers from authoritative systems where available; use aliases only as aliases. Do not let string similarity merge entities that affect permissions, source selection, calculations, or release evidence.

For ambiguous semantic resolution, record a proposed merge with supporting evidence and a reversible mapping. Keep both original records addressable. A false merge can contaminate many downstream conclusions, which is a central warning in the anchor. [D1: pp. 5, 10]

Two time dimensions and two kinds of validity

Record when the system learned something separately from when it was applicable. A vendor capability observed today may describe an older version. An evaluation from last week can remain a valid historical observation even when it no longer qualifies the current candidate. Supersession should change applicability, not erase the past.

Pin edge endpoints to versions when the relationship is version-specific. For example, evaluation-42 EVALUATES candidate-B is precise. evaluation-42 EVALUATES latest is not. Preserve the source range, environment, and dependency manifest used by the evaluation.

Validation before publication

Accept graph-update proposals through a trusted validator that checks schema, endpoint existence, project scope, permissions, source versions, expected graph revision, and duplicate identity. Type-correct output can still be false: extracted semantic relations should retain an uncertainty or candidate status until their evidence policy is satisfied. Never treat a model's confidence number as a calibrated probability by default.

Allow ordinary knowledge cycles where meaningful. Detect cycles in prerequisite dependencies and contradictory current-version claims; neither should be silently treated as executable readiness. When dependency information is incomplete, use conservative scoped invalidation and explain the uncertainty rather than promising perfect impact analysis.

07Implementation proposal

Build context, do not dump memory

The goal is a small starting context with accessible supporting evidence, not a smaller but misleadingly complete summary.

The anchor recommends resolving task entities, traversing a bounded neighborhood, including current versions, prioritizing relevant verified claims, retaining conflicts, and serializing within a token budget. Anthropic's context guidance similarly emphasizes selective context and external notes rather than indiscriminate accumulation. [D1: p. 7][R6]

Ingest in order of reliability

First, import explicit structure. Repository IDs, commit parents, issue references, declared dependencies, build manifests, and captured test results are generally better handled by deterministic adapters than model extraction. Store source versions and connector cursors so a refresh can detect change and deletion.

Second, extract semantic claims only where they help. Architecture decisions, incident narratives, review rationale, and unresolved questions may need model interpretation. Keep the extracted statement tied to a source range. Treat an agent's summary as a derivative record, not a replacement for the source. Anthropic's cookbook demonstrates extraction, resolution, and provenance-aware querying; the publication policy here is a proposed additional control. [R5]

Third, maintain the index incrementally. Reprocess changed source snapshots, not the full repository on every turn. Mark broken links, revoked access, or unavailable sources honestly. A content hash protects identity, not truth. Failed ingestion must not leave the system claiming that a stale index is current.

A reusable retrieval sequence

Resolve the task and enforce the access boundary

Establish project, repository, tenant, source versions, and allowed disclosure destination. Exclude inaccessible records before traversal and before context is sent to any provider.

Include mandatory controls and interfaces

Always include the approved outcome, acceptance criteria, current capability policy, input manifest, shared contracts, and known high-impact counterexamples. These are not optional top-k search results.

Retrieve the task neighborhood

Follow allowed dependencies, relevant decisions, prior attempts, and supporting or contradictory evidence. Combine graph traversal with keyword or semantic search when explicit links are incomplete.

Rank and pack under an explicit budget

Prefer applicable evidence over merely recent prose. Keep file references and source ranges. Include an omission manifest with why records were excluded and how the worker can retrieve them.

Check sufficiency before work begins

If required controls or interfaces do not fit, split the task or request a bounded expansion. Never truncate permissions, contradictory evidence, or a necessary prerequisite without disclosure.

Packet structure

A practical packet contains a stable header, the task contract, a pinned baseline, relevant architecture, evidence and counterexamples, open questions, tool policy, and a retrieval manifest. Store its content hash, builder version, source snapshot IDs, policy revision, and model-independent token estimate. The actual provider tokenizer may differ; record actual usage separately.

Give the reviewer the acceptance contract, candidate diff, actual test evidence, and relevant architecture. Do not automatically include the implementer's persuasive narrative. A reviewer can request it when useful, but should first inspect the artifact and requirement independently.

Evaluate retrieval as part of the product

Create a small set of restart and change-impact questions with expected relevant records. Measure whether the packet includes critical evidence, preserves conflicting facts, avoids wrong-project material, and permits an answer with valid support. A low token count is not a success when it removes the reason a change is unsafe.

08Implementation proposal

New projects: establish a thin delivery backbone

Begin with the smallest end-to-end behavior that proves the architecture and the evaluation path. Let the graph grow from real work.

A new project has little historical evidence but many untested assumptions. The main risk is an elaborate plan whose interfaces, user experience, and integration assumptions have never been exercised. Use a discovery-and-delivery sequence that records decisions without pretending the whole architecture is already settled.

Write a charter with explicit authority

Define the user, core journey, success measures, non-goals, supported operating environment, data sensitivity, and actions requiring approval. Separate product ambition from the first qualification envelope.

Identify uncertainty and run bounded spikes

List assumptions about external APIs, numerical methods, UI feasibility, licensing, deployment, or authentication. Use small experiments with explicit questions and stopping criteria. Preserve rejected approaches with the conditions under which they failed.

Build the executable baseline

Provide a reproducible environment, a command to start the application, an offline fixture, a smoke test, and a test evidence format. Capture the first known working baseline before expanding scope.

Deliver one vertical slice

Connect a real user action through the interface, backend, storage, and one integration boundary. Use a fake only where that boundary is explicitly not yet qualified; mark its limitation. Avoid completing every backend module before testing a user journey.

Derive bounded packets from the slice

Break future work around observable outcomes and contract boundaries. Add dependency edges only when they express a real requirement. Capture the acceptance evidence required at each gate.

Prove a cold restart before expanding autonomy

A fresh agent must find the baseline, start the application, identify the next eligible packet, and explain current limitations without the old conversation. Repair the handoff system before adding more workers.

The initial graph can be very small

Start with the charter, a few acceptance criteria, the first baseline, important architecture decisions, bounded tasks, and their evidence. There is no need to infer relationships for every file, class, dependency, or comment. Expand the schema when an actual question cannot be answered by existing records.

Anthropic's long-running harness work supports the value of explicit initialization and incremental handoff artifacts. The specific sequence above is an adaptation for multi-module projects, not a proven universal order. [R3]

New-project exit gate
Before unattended feature work, demonstrate a real vertical slice, a reproducible evaluation command, a known working baseline, and a successful fresh-context handoff. Open domain or external gates stay visible; they need not prevent unrelated discovery work.
09Implementation proposal

Existing projects: preserve reality before reorganizing it

The first problem is often not missing code. It is disagreement among the checkout, issue tracker, local work, deployed behavior, and historical notes.

A mature or partially implemented project needs an adoption process that does not erase useful work or invent a new source of truth. Treat bootstrap as a read-mostly reconciliation exercise. Do not let an agent "clean up" dirty files, reset branches, rewrite history, or close broad issues just to make the new execution graph appear orderly.

Inventory every relevant working state

Identify repositories, local HEADs, worktrees, dirty files, untracked artifacts, important unpublished commits, deployed versions, and existing instructions. Take an appropriate backup or snapshot before changes. Do not assume remote main is the newest valid integration.

Adopt a baseline explicitly

Record the chosen revision or multi-repository manifest, why it is authoritative, what local work is excluded, and which capabilities are implemented but unverified. Stop dependent implementation if the expected integration cannot be found.

Run a bounded health and characterization pass

Record the environment, test commands, outcomes, existing failures, and a representative user journey. Use characterization tests to preserve behavior, while noting that preserved behavior can include defects and is not automatically correct.

Reconcile historical claims with current evidence

An old defect may already be repaired; a closed issue may have only a mock demonstration. Re-run the relevant counterexample at the adopted baseline. Keep the old record and append the new conclusion with scope and versions.

Create a shadow index

Import explicit task dependencies, canonical issue IDs, architecture decisions, and existing evidence. Leave the authoritative tracker unchanged initially. Compare readiness and impact answers against an experienced maintainer's assessment.

Pilot one bounded maintenance or feature slice

Run a graph-assisted context handoff and review against current conventions. Promote the index from shadow mode only after it improves recovery or correctness without breaking the team's workflow.

Brownfield exit gate
A maintainer and a fresh agent agree on the adopted baseline, preserved local work, unresolved conflicts, and next eligible task. Existing evidence has not been silently promoted, discarded, or replaced.
10Implementation proposal

Turn a roadmap into executable work packets

A good packet is small enough to evaluate, large enough to deliver coherent behavior, and explicit about what it must not change.

Use three levels: product outcomes define what users need; delivery packets define coherent, independently reviewable slices; and local implementation steps are the worker's temporary plan. Keep the first two durable. Do not turn every function edit into a permanent top-level agent task.

Split by behavior and uncertainty

"Implement storage" is often too broad. "A saved analysis reopens with the same input versions, findings, and unresolved questions after process restart" is evaluable. It naturally includes storage, schema, and integration tests without prescribing every internal function.

Separate a feasibility spike from production implementation when its result could change the architecture. Separate a pure refactor from new domain semantics when combining them obscures regression causes. Keep tightly coupled interface changes together when splitting them would force both agents to reason from half a contract.

Dependencies should express the required evidence level

A later task may need only a stable interface contract to begin coding, but require real integration evidence before qualification. Model those separately. An external account gate should not block every offline test; it must still block the specific conclusion that requires that account. A parent feature is not complete merely because a pilot subset passed.

Detect prerequisite cycles before execution. Resolve a true cycle by extracting a shared contract, creating a bounded integration packet, or making an explicitly provisional interface decision. Do not break the cycle by silently marking one prerequisite complete.

A useful definition of readiness
A packet is eligible only when its contract is approved, its required prerequisites satisfy the specified gate levels, its inputs are current, its resources and budget are available, its capability policy permits the work, and no conflicting writer holds the required scope.
11Implementation proposal

Run, stop, recover, and resume honestly

Durability is more than saving a conversation. It is knowing which operation ran, against which state, with what result, and whether repeating it is safe.

Keep a durable task state, immutable attempt records, and a compact event history. Ordinary code should validate readiness, reserve resources, start workers, collect process results, and enforce stopping rules. Models should handle the judgments that are actually uncertain, such as interpreting a requirement or diagnosing a conceptual defect.

The minimum scheduler contract

Claim a task atomically so two supervisors cannot start the same write scope. A lease should identify the holder, expiry, attempt, and a monotonically changing fencing token or equivalent protection. Merely expiring a timestamp does not stop an old process: reject late publications from stale leases, and reconcile any process that may still be running before starting a replacement.

Pin each attempt to its input manifest, policy revision, prompt/routing version, and actual provider/runtime configuration. Keep attempted, running, interrupted, failed, cancelled, and completed states distinct. A process that exited successfully still needs its output contract and evidence checked.

Checkpoint boundaries

Useful checkpoints are after baseline adoption, context construction, candidate creation, evidence collection, review, and accepted publication to the local ledger. A restart should inspect the last durable state, compare it with the filesystem and remote systems, and resume only the missing safe work. Never infer that an operation did not happen simply because the acknowledgement is absent.

LangGraph's current documentation distinguishes persistent checkpointers from in-memory examples; an in-memory saver loses state on process restart. Its interrupt documentation also says that code before a resumed interrupt can run again. Framework-level persistence therefore does not remove the need to design safe side effects. [R9][R10]

Handle external effects explicitly

Classify operations as read-only, safely idempotent, conditionally repeatable, or non-repeatable. For a mutating action, record the intended request, authorized target, expected source version, idempotency key when supported, and outcome. If a timeout leaves the result ambiguous, inspect remote state before replay. Do not promise exactly-once external behavior when the external system provides no such contract.

A database transaction cannot generally make a remote API call and a local artifact write atomic together. Use a recoverable operation journal, staged publication, or outbox-style processing as appropriate. Store pending versus confirmed status. A compensating action is not guaranteed rollback: the original effect may already be visible to other users.

Cancellation and budgets

Cancellation should acknowledge the request, signal managed processes, and report whether work actually stopped. Do not clear a lease while a writer can still mutate shared state. A timeout, provider limit, or repeated conceptual failure should produce the best preserved candidate, the evidence collected, missing gates, and a focused escalation question.

Enforce total model calls, worker starts, tools, elapsed time, and usage at the trusted runner or gateway where those controls are available. Count child agents, retries, and repair calls toward the same parent budget. When exact usage arrives late, reserve conservatively and stop new work before consuming the margin; do not call an advisory prompt a hard cap.

The cold-restart test
Kill the runner after candidate creation, after evaluation, and during an ambiguous external operation in a sandbox. The next session must recover the exact candidate and evidence state, avoid duplicate writers, and refuse unsafe replay. A successful clean-path demo is not enough.
12Implementation proposal

Use roles and parallelism where they add signal

A role is a bounded responsibility, not necessarily a permanently running agent. Default to one writer per shared integration scope.

Safe candidates for early parallelism

Read-only audits of disjoint components, independent test-gap analysis, competing design proposals, or document extraction over separate sources can be reasonable pilots. Isolated code changes are candidates only after interfaces and file ownership are understood. Different directories do not prove independence: two changes can still alter the same schema, resource budget, or behavioral invariant.

Worktrees separate working directories; they are not a security sandbox. Workers can still collide through shared databases, caches, ports, credentials, external accounts, or generated files. Give each worker separate fixtures, processes, temporary directories, and resource limits where required.

Review independence has limits

A fresh session can reduce anchoring on the implementer's narrative, but the same model family can repeat the same misconception. Even different models can share blind spots. Use differently framed checks, counterexamples, direct application interaction, and independently established expected results. For numerical or domain-sensitive work, agreement between agents is not a substitute for an oracle.

Do not reset a productive implementer on an arbitrary schedule. Reset or hand off at meaningful boundaries when context quality, reproducibility, or review independence benefits. Anthropic's later harness experiments show why this policy should be revisited as models improve: some earlier decomposition and reset scaffolding became unnecessary. [R7]

Define reduction before expansion

The reducer must know how to merge duplicate findings, preserve contradictory findings, reject unsupported assertions, and account for every assigned unit. A stopped or failed worker is a coverage gap, not a negative result. An empty result set may mean no findings, incomplete coverage, or failed analysis; distinguish them explicitly.

Optimize accepted outcomes, not agent activity

Graph memory may reduce repeated context and rediscovery, but indexing, maintenance, verification, and orchestration also consume resources.

The source requires explicit limits on calls, agents, tools, time, tokens, cost, retries, and graph writes. It also warns that parallel workflows can increase activity without increasing value. The correct objective is useful, accepted progress under a quality and risk constraint. [D1: pp. 8-9]

Keep the full cost ledger

Record actual provider/model identifiers, input and output usage, cached versus uncached categories when reported, tool/runtime consumption, reviewer and repair work, graph upkeep, and human interventions. Distinguish measured data from estimates and unavailable counters. Do not translate a subscription limit into an invented per-token price.

Total effort = preparation + implementation + context/retrieval + verification + repair + integration + graph maintenance + human intervention

Use cost per independently accepted outcome and time to accepted vertical slice as primary operational measures. Criteria differ in difficulty, so compare similar scopes or report by task family. Never reward agents for splitting one requirement into many easy checkboxes.

Suggested autonomy tiers

TIER A

Read and analyze

Read approved sources, run offline analysis, and prepare proposals. No implicit publication or broader disclosure rights.

TIER B

Modify an isolated candidate

Edit a named worktree and run bounded local tools. No access to production state; shared policy and release operations remain protected.

TIER C

Publish a reviewed result

Push, merge, deploy, or mutate an external system only under separate scoped authorization tied to the actual candidate and target.

These tiers are a proposed policy vocabulary, not universal assurance levels. A nominally read-only task can still disclose private data to a provider; outbound access needs its own policy. A local command can still access credentials or the network unless the runtime prevents it.

Make approvals precise and expirable

An approval should identify the action, artifact/version, target, allowed scope, prerequisite evidence, approver, and validity window. A new commit, different destination, or changed risk can require reapproval. Do not treat approval of a plan as blanket approval of every later side effect.

Durable does not mean immortal

Keep logical audit continuity without promising indefinite retention of all source data. The anchor's addressable-supersession principle can be implemented using tombstones and retained non-sensitive metadata when payload removal is necessary. Backups and derived caches must follow the same data policy; deleting one graph node does not necessarily remove all copies.

BUSINESS WORKFLOW

Approval and notification software

DATA PLATFORM

Across all three domains, identify the immutable source, the mutable interpretation, the versioned artifact, the evaluator, and the authority required for consequential action. bounded-program.md

A provider-neutral control brief for a bounded development session. It is not a runtime or a permission grant.

# Bounded development run

This is an operating contract template, not permission to execute.
Execution is disabled until the project owner approves a completed packet
and the runtime confirms all required controls can be enforced.

## Before work
1. Read the approved task and policy references; verify their revisions.
2. Inspect the actual baseline and preserve dirty files and worktrees.
3. Verify required prerequisites, capability scope, and budget reservations.
4. Read the generated context packet and its omissions and conflicts.
5. Stop if mandatory evidence or the expected integration is unavailable.

## During work
- Work on one approved packet in the assigned isolated scope.
- Reuse existing architecture and interfaces unless the packet authorizes change.
- Do not alter protected evaluation or permission policy.
- Record candidate artifacts with exact inputs and versions.
- Run registered verification commands; retain actual output and exit status.
- Propose graph updates with sources and uncertainty. Do not self-certify them.
- Count all descendants, tool calls, retries, and repairs against aggregate limits.
- Do not send private data to an undeclared destination.

## Review and repair
- Supply the exact candidate, diff, criteria, and observed evidence.
- A fresh reviewer returns criterion-level defects and unresolved gates.
- Make only bounded repairs within the remaining budget.
- A changed candidate requires reassessment of affected evidence.
- Escalate repeated conceptual failure instead of widening scope silently.

## Stop conditions
Stop on exhausted limits, missing authority, unsafe or ambiguous external
state, unresolved baseline identity, or repeated non-progress.
Preserve the best candidate, evidence, failed approaches, and next safe action.
A stopped, blocked, or skipped check is never a pass.

## Publication
No push, merge, deployment, purchase, or external-source mutation is
inherited from this document. Each requires its own scoped authorization.

## Return
Return a structured run receipt plus a concise human summary:
what changed; exact candidate; what passed; what failed or was unrun;
remaining questions; actual usage or unknown counters; next safe action.

Recommended order of use

Start with the charter, one packet, and its receipt. Add decision and escalation records as real questions arise. Keep evaluator ownership separate from the implementer's routine edits. Adopt the pilot plan only after the actual runtime can enforce the required limits and preserve state.

A generated context packet and a run receipt can be stored as files initially. If multiple processes must update them, introduce transactional ownership rather than relying on concurrent edits to shared JSON. Terms used in the report

Agent
A model-driven process that can reason about a task and invoke a permitted set of tools.
Harness
The surrounding software that supplies context, tools, limits, verification, and lifecycle management.
Node / edge
An identifiable record and a typed relationship between records.
DAG
A directed acyclic graph. Commit ancestry and prerequisite ordering can be DAGs; not all workflow or knowledge graphs are.
Provenance
Where a statement or artifact came from, which version and run produced it, and what evidence supports it.
Epistemic status
Whether a record is an observation, hypothesis, inference, confirmed intent, or accepted decision.
Context packet
A task-specific bundle of controls, current source references, relevant evidence, and visible omissions.
Work packet
A bounded, versioned obligation with a defined outcome, prerequisites, evidence contract, and limits.
Receipt
A structured record of an actual attempt, artifact, command, evaluation, usage, and remaining uncertainty.
Oracle
An independently established expected answer or property used to evaluate correctness.
Lease / fencing token
A time-bounded claim on work plus a mechanism that lets the system reject stale owners or late publications.
Idempotency
A defined guarantee that retrying an operation does not create an additional unintended effect.
Reducer
A stage that combines, deduplicates, checks, and accounts for the results of parallel workers.
Qualification envelope
The explicitly supported methods, inputs, environments, and behaviors covered by the evidence.
Supersession
A newer record replaces the current applicability of an older one without silently deleting its history.
Cold restart
Continuation by a fresh process or session using durable project state rather than the previous conversation.

Can a fresh contributor trace every important output to its objective, source versions, artifact, run, evaluation, and unresolved limits? If not, improve the records and controls before adding more agents.
